# Bundled Linux native window candidate (#688)

The selected contract is GTK3 + WebKit2GTK 4.1 inside the x86_64 AppImage, including GI in the frozen launcher and the standalone Python used after source handoff. Playwright WebKit remains a separate browser-tool dependency. This candidate is not natively qualified yet.

Build the closure on Ubuntu 22.04 x86_64. `build_linux.sh` installs the locked `linux-desktop` extra into both interpreters; `Ouroboros.spec` collects GI's typelib graph. After freezing, `scripts/bundle_linux_gtk.py` copies the declared Debian package resources and recursive ELF dependencies, package notices, common license texts, WebKit helpers, GIO TLS modules and GStreamer plugins into `_internal/linux-gtk`. libgirepository reads `GI_TYPELIB_PATH` first and then, silently, its compiled `/usr/lib/x86_64-linux-gnu/girepository-1.0` and Debian's `/usr/lib/girepository-1.0` (gobject-introspection 1.72.0-1), and it loads each typelib's header dependencies eagerly. The builder therefore refuses a shipped typelib whose dependency typelibs are not shipped too, and ships every library a typelib names, so the builder's own `/usr` cannot hide a gap that would break a host without `gir1.2-*` packages; Jammy's `Pango-1.0.typelib` requires `HarfBuzz-0.0`, which `gir1.2-harfbuzz-0.0` supplies. A GI extension may name libpython only if its own interpreter ships that file; the builder's libpython is never copied. The closure manifest records package versions, binary/source-package versions, file hashes, host-library exceptions and relocation edits. `_internal` library aliases point to that same closure, preventing PyInstaller from loading a second GLib/WebKit stack. The AppImage packer refuses a payload without the manifest.

AppRun sets the loader path before exec. `desktop_media.prepare_linux_bundle` restores resource paths after PyInstaller's GI hooks and selects GTK even in a KDE session. In the Jammy `webkit2gtk` 2.50.4 source, release builds ignore the developer-only `WEBKIT_EXEC_PATH` (`ProcessExecutablePathGLib.cpp`) and start every helper from the compiled `PKGLIBEXECDIR` through `g_subprocess_launcher_spawnv` without setting a working directory (`ProcessLauncherGLib.cpp`); the web process opens its injected bundle under `PKGLIBDIR`, which Debian builds as the same directory. The builder replaces bounded, NUL-delimited `/usr` prefixes of those paths and of the dormant bubblewrap/xdg-dbus-proxy helpers with equal-length `././` prefixes; offsets and lengths stay fixed. Read offline, the 2.50.4 package library carries three of the listed prefixes at four sites, while the `libexec` and `share` alternatives are absent and left alone; the native manifest records the actual edits. A relative path resolves against the spawning process's cwd, so the desktop shell keeps `_internal/linux-gtk` as its cwd, including after the existing source-launcher exec, and neither the launcher nor pywebview 5.4 changes it afterwards. Server processes already choose their repo cwd; CLI dispatch retains the caller's cwd. These are source and byte expectations, not execution proof. Missing display/backend still uses the existing browser fallback, bridge and close paths.

The OS supplies the kernel, glibc/loader, X11 or Wayland session, graphics drivers, fonts and trust store. GTK, WebKitGTK, GI, Soup, ICU and TLS libraries are shipped. The first proposed qualification is Ubuntu 22.04 x86_64 with a mapped X11 window on Xvfb/Openbox. It cannot establish physical-GPU, Wayland, Fedora/Astra/RED OS, microphone or broad codec compatibility. No sandbox-disable environment variable is added. Driver ABI interactions and payload size need the native result.

WebKit's web-process sandbox is off in this design because WebKitGTK's 4.1 API defaults it off, not because of any switch. In 2.50.4, `WebProcessPool` starts with `m_sandboxEnabled { false }`; only the 6.0 API (`ENABLE(2022_GLIB_API)`) enables it for every context, and the 4.1 API leaves it to `webkit_web_context_set_sandbox_enabled`, which pywebview 5.4's GTK backend never calls (it uses `WebContext.get_default()`). WebKit therefore starts `WebKitWebProcess` directly, as for any pywebview 5.4 GTK window on WebKitGTK 4.1. The qualifier records the observed mount namespaces and any bubblewrap/xdg-dbus-proxy process and requires neither outcome. The shipped `bwrap` and `xdg-dbus-proxy` and their relocated paths stay dormant. Enabling the sandbox is a separate security and packaging decision: `BubblewrapLauncher.cpp` passes `PKGLIBEXECDIR` as both bind source and destination, and a relative relocated prefix has not been qualified there.

## Parent-run bounded experiment

`.github/workflows/linux-appimage-native.yml` is dispatch-only, read-only, secretless and separate from the release graph. The parent must first register the ignored `build/issue688-evidence-r2` evidence (R1 is already registered), then capture this patch in a research branch/commit. Dispatch that exact branch with `candidate_sha` equal to its 40-character HEAD; the workflow checks both checkout and event SHA. The delegate does not push or dispatch.

```bash
gh workflow run linux-appimage-native.yml --ref <research-branch> -f candidate_sha=<exact-sha>
```

The workflow is bounded to 120 minutes (90 build, 18 native). `native-qualification.Dockerfile` uses the digest-pinned Ubuntu image with the ordinary Ubuntu archive, accepted only with the image's archive keyring (`signed-by`). The dated `snapshot.ubuntu.com` endpoint returned 503 for every suite in run 39601252706, so apt inputs are whatever the archive serves during the build and are not reproducible. The image's own packages are upgraded first because `apt-get source` can fetch only versions the archive still lists; the build keeps the signed `InRelease` files present at its start (`apt-release/`), the installed package list and the manifest's exact binary and source-package versions. uv 0.12.1 has its own digest, Python/Node/Betterleaks/Claudexor retain repository pins, and `uv.lock` pins Python inputs. Build-system dependencies resolved while compiling sdists are not a bit-reproducible lock either: preserve build logs, exported requirements, final package inventory and artifact digest on every run. The normal release-tag guard is untouched. The experiment creates a tagless diagnostic bootstrap seed and uses the production spec, closure builder and AppImage packer; it never publishes, attests, signs, tags or installs the product on the runner.

Build and qualification run under `safe_test` with disposable roots outside Git and no project installation into the dependency environment. The clean desktop container receives only the candidate source and output artifacts, has no installed GTK3/WebKitGTK/GI, no build-library mounts, no host display socket, no external network and runs as a non-root user. Docker's default seccomp filter is lifted only so that a bubblewrap attempt, if WebKit made one, would be observed rather than refused by Docker; the container is not privileged and no WebKit sandbox variable is set either way. This condition is part of the evidence, not a claim about the default Docker sandbox.

`qualify_linux_appimage.py` starts the actual AppImage, closes Setup without configuring a provider, and requires a mapped Main window, screenshot, genuine JavaScript → `MainApi.shell_info()` roundtrip, bundled GTK/WebKit library maps and live bundled WebKit web/network helpers. It records the web process's mount namespace beside the launcher's, plus any bubblewrap/xdg-dbus-proxy process, in `webkit-sandbox.json` without requiring either outcome. A saved HTML suffix instruments only the disposable managed page. It then records a comment-only local fixture commit and repeats through production source handoff, checking the standalone Python executable and bridge source identity. This is cold source handoff, not a live update-feed or restart test. No-display and deliberately removed-typelib cases must report browser fallback and stop cleanly. The artifact is not modified for the damaged-backend negative; that case runs a separately extracted copy. All cases use private ports/state and check ordinary close/TERM cleanup; none calls Panic or a model.

It includes the AppImage and SHA-256, seed/source identities, GTK manifest, matching Debian source archives with hashes, container identities, package lists, raw logs, JUnit, process maps, bridge replies and screenshots.
